# Логистическая CRM: запуск и устройство

## Завершение установки: короткая инструкция

На рабочем сервере выполняйте команды из папки, где уже лежат `.env` и
`docker-compose.yml` бота. Подготовленный архив `hector-crm-release.zip` содержит
только код, без токенов и тестовых данных.

1. Сделайте резервную копию и остановите старый бот:

   ```sh
   docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > "backup-before-crm-$(date +%Y%m%d-%H%M%S).sql"
   docker compose stop bot
   ```

   Убедитесь, что первая команда завершилась без ошибки и файл копии не пустой.

2. Загрузите `hector-crm-release.zip` на сервер и распакуйте в эту же папку проекта
   с заменой файлов кода. Сохраните рабочий `.env`, `logs` и volume PostgreSQL.
   Затем соберите и запустите:

   ```sh
   docker compose up -d --build
   docker compose ps
   docker compose logs --tail=50 migrate backend
   curl -f http://127.0.0.1:8000/health/ready
   ```

   Ожидается `status: ok`, `revision: 014`. Если сборка или миграция завершилась
   ошибкой, не продолжайте выпуск токенов: сохраните последние строки ошибки.

3. Выпустите два разных токена, заменив слова `GUILD_ID`, `BOT_ID`, `YOUR_ID`
   числовыми ID сервера Discord, бота и вашего аккаунта:

   ```sh
   docker compose run --rm backend python -m backend.manage issue --guild GUILD_ID --user BOT_ID --name discord-service --role BOT
   docker compose run --rm backend python -m backend.manage issue --guild GUILD_ID --user YOUR_ID --name Administrator --role ADMIN
   ```

   Токены показываются один раз. Первый запишите на сервере в `.env` как
   `BACKEND_TOKEN=...`, рядом добавьте `BACKEND_URL=http://backend:8000`.
   Выполните `docker compose up -d bot`. Второй токен понадобится для Desktop.
   Не заменяйте им существующий `DISCORD_TOKEN`.

4. На своём ПК откройте PowerShell и оставьте работающим SSH-туннель:

   ```powershell
   ssh -L 8000:127.0.0.1:8000 USER@SERVER
   ```

   Замените `USER@SERVER` своими SSH-логином и адресом сервера. Запустите
   `start-desktop.cmd` двойным щелчком. Адрес — `http://127.0.0.1:8000`,
   токен — второй, ADMIN. Discord bot token в Desktop вводить не нужно.

5. В Desktop → **Discord** укажите ID канала панели, канала логистов и категории
   приватных уведомлений. Сохраните настройки, настройте роли и нажмите
   **Создать / обновить панель**. ID копируются в Discord при включённом
   режиме разработчика. Боту нужны права отправки сообщений, embeds, чтения
   истории и управления каналами для приватных уведомлений.

6. Создайте пробный заказ через панель Discord. Примите его в CRM, создайте
   задачу производства, отметьте готовность. На складе заведите небольшой
   тестовый остаток, создайте резерв и освободите его. Завершите задачу,
   переведите заказ через «Готов» в «Выполнен» и проверьте DM заказчика.

Ниже приведены подробности прав, работы склада и диагностики. Не выполняйте
`docker compose down -v`: это удаляет рабочий volume БД.

Существующий бот дополнен FastAPI backend и приложением PySide6. Новые заказы
создаются через постоянную панель Discord и хранятся отдельно от старых тикетов.
Desktop работает только через HTTP/WebSocket: ему не нужны PostgreSQL, Discord
bot token или библиотеки Discord. Старые тикеты, роли, набор и команды сохраняются.

## Что реализовано

- Корзина Discord: категории, поиск по общему каталогу/алиасам, несколько позиций,
  штуки и ящики, редактирование количества, доставка, комментарий, подтверждение.
  Доставка и другие запросы допускают свободный текст. Лимит — 30 позиций.
- Подтверждение идемпотентно; исходная панель остаётся. Неподтверждённая корзина
  существует в памяти до 15 минут и не переживает рестарт бота.
- Канал логистов с кнопками принятия, просмотра и отклонения. Persistent views
  восстанавливаются после рестарта. Закрепление за принявшим логистом атомарно.
- Таблица и Kanban, поиск, фильтры по статусу, ответственному, заказчику, категории
  и дате, карточка, изменение количества/доставки, история и внутренние заметки.
- Десять статусов; переходы проверяет backend. Drag & drop отправляет запрос,
  а конфликт версии возвращает актуальные данные. ADMIN может сделать переход
  вне графа с обязательной причиной. Закрытые заказы нельзя редактировать.
- Уведомления заказчику в DM; при закрытых DM — отдельный приватный канал.
  Внутренние заметки в уведомления не попадают.
- Dashboard, общий калькулятор, настройки каналов/ролей, обновление каталога,
  алиасы, overrides, просмотр/отзыв токенов, журнал, повтор неотправленных заданий.

Склад, резервы и производственные задачи доступны отдельными страницами Desktop
(подробности ниже). Маршруты доставки пока не реализованы. Старые тикеты
автоматически в CRM не конвертируются.

## Сервер через Docker Compose

Используйте Python 3.11 для локального сервера; контейнеры уже используют его.
Сначала сохраните резервную копию существующей БД по инструкции DEPLOY.md.
Не заменяйте рабочий `.env` примером и не удаляйте существующий `postgres_data`.

```sh
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 migrate backend
```

Сервисы: `db`, одноразовый `migrate`, `bot`, `backend`. Миграции 010–014 добавляют
новые таблицы; бот и backend запускаются после их успешного выполнения.
Backend опубликован только на `127.0.0.1:8000` сервера. `/health/live` проверяет
процесс, `/health/ready` — доступность БД и актуальность схемы Alembic.

В `.env` по умолчанию пусты `BACKEND_URL` и `BACKEND_TOKEN`: старый бот продолжает
работать, новая интеграция включается после выпуска сервисного токена.
Сервер Discord должен уже присутствовать в таблице `guilds` существующего бота
(обычная настройка `/hec-setup`). Токены выпускаются только на сервере:

```sh
docker compose run --rm backend python -m backend.manage issue --guild GUILD_ID --user BOT_USER_ID --name discord-service --role BOT
docker compose run --rm backend python -m backend.manage issue --guild GUILD_ID --user YOUR_DISCORD_ID --name Administrator --role ADMIN
```

Замените идентификаторы числовыми Discord ID. Каждая команда показывает токен
один раз и его ID для отзыва. Срок по умолчанию — 90 дней; `--days` меняет срок.
В БД хранится только SHA-256 случайного токена. Для каждого сотрудника выпускайте
отдельный токен с его Discord ID и ролью, а не общий административный ключ.

Укажите в серверном `.env`:

```dotenv
BACKEND_URL=http://backend:8000
BACKEND_TOKEN=<токен BOT>
```

Затем `docker compose up -d bot`. В Desktop используйте личный токен ADMIN,
а не BOT и не Discord bot token. Настройте на странице Discord канал панели,
канал логистов, категорию приватных уведомлений и связи ролей. Нажмите
«Создать / обновить панель» или выполните `/orders-panel` в Discord.
Боту нужны доступ к каналам, отправка embeds, чтение истории, а для fallback —
управление каналами. В категории создаются каналы с доступом заказчика и бота;
серверные администраторы Discord также имеют доступ по правилам Discord.

Одна конфигурация `BACKEND_TOKEN` связывает новую интеграцию с одним сервером.
API и таблицы изолируют несколько guild; старые функции бота сохраняют прежнюю
поддержку серверов. Для нескольких CRM guild одному процессу понадобится
расширение конфигурации подключений.

## Desktop на Windows

Для запуска двойным щелчком используйте `start-desktop.cmd`. На текущем ПК он
использует уже проверенное окружение `.venv`; на новом ПК при установленном
Python 3.11 создаст отдельное `.venv-desktop` и установит зависимости PySide6.

В каталоге репозитория:

```powershell
py -3.11 -m venv .venv-desktop
.venv-desktop/Scripts/python.exe -m pip install -r requirements-desktop.txt
.venv-desktop/Scripts/python.exe -m desktop.app
```

Для сервера на другом компьютере используйте HTTPS или SSH-туннель:

```sh
ssh -L 8000:127.0.0.1:8000 USER@SERVER
```

При туннеле адрес в Desktop — `http://127.0.0.1:8000`. Для прямого подключения
настройте TLS reverse proxy; пример WebSocket-настроек есть в `nginx/nginx.conf`.
Этот шаблон сам сертификат не получает и не запускается текущим Compose.
Удалённый HTTP Desktop отклоняет. URL сохраняется в QSettings, токен — только
в памяти до закрытия приложения. Вводить его нужно при каждом запуске.

## Права

| Роль | Действия |
|---|---|
| ADMIN | Все действия, настройки, credentials, переход с причиной |
| MANAGER | Заказы любых логистов, заметки, алиасы, просмотр администрирования |
| LOGISTICIAN | Принять новый заказ; менять свободные и свои заказы |
| PRODUCTION | Переходы в ожидание ресурсов, производство и готовность по графу |
| DELIVERY | Переходы в доставку и завершение по графу |
| VIEWER | Чтение CRM и калькулятора |
| BOT | Сервисные сообщения; действия пользователя через проверенный Discord actor |

Обычный игрок получает CUSTOMER только через бот: доступ к собственным заказам,
без внутренних заметок. Для Desktop CUSTOMER-токены не выпускаются. Связи ролей
Discord применяются к действиям через бота; роль личного Desktop-токена задаётся
при выпуске. Изменение Discord-роли не меняет уже выданный Desktop-токен:
отзовите его и выдайте новый. Существующие глобальные StaffRole используются
как fallback, Discord Administrator получает ADMIN через доверенный BOT транспорт.
Пользовательские заголовки обычного Desktop-токена не повышают его права.

Отзыв токена из CLI, в том числе текущего административного:

```sh
docker compose run --rm backend python -m backend.manage revoke CREDENTIAL_ID
```

## Локальный backend без Docker

```powershell
py -3.11 -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-backend.txt
$env:POSTGRES_HOST='127.0.0.1'
# Остальные POSTGRES_* задайте для нужной БД в окружении или .env.
.venv/Scripts/python.exe -m alembic upgrade head
.venv/Scripts/python.exe -m uvicorn backend.app:create_app --factory --host 127.0.0.1 --port 8000
```

По умолчанию адрес БД строится из `POSTGRES_*`, как в старом проекте.
Чтобы использовать именно `DATABASE_URL`, явно установите
`DATABASE_URL_MODE=explicit`. Старая случайно оставшаяся переменная DATABASE_URL
не переключает рабочую БД. В Compose принудительно используется `components`.
Standalone-бот сохраняет запуск миграций; `DB_MIGRATE_ON_STARTUP=false` отключает
его после внешнего применения схемы. БД с таблицами без Alembic revision требует
ручной сверки схемы; автоматического `stamp` больше нет.

## Калькулятор и источники

Повторно используются существующие FoxholeHQ provider, дополнительный Wiki
provider, ItemCatalogService, ItemResolver и CalculatorService. Отдельного
провайдера/калькулятора для CRM нет. `/calc` при подключённом CRM вызывает API;
в автономном режиме использует тот же сервис планирования локально.

FoxholeHQ фактически отдаёт HTML и данные страницы factory; это не выдуманный
JSON REST API. Ключ FOXHOLEHQ_API_KEY для текущего источника не требуется.
Живая проверка 08.09.2026: объединённый каталог — 392 предмета, 680 рецептов,
версия `Patch 66 + Foxhole 1.66`. Spatha получена из Wiki, включая базовую Falchion.
Наличие всех PAD/Construction Yard/Shipyard рецептов источники не гарантируют:
показываются доступные рецепты, отсутствующая стоимость не выдумывается.

Снимок расчёта сохраняется с позицией: единица, количество, варианты производства,
источник/версия, размер ящика, материалы. Обновление кэша не переписывает уже
созданный заказ. Редактирование состава явно создаёт новый снимок и историю.
Старые overrides и новые FoxholeRecipeOverride учитываются без изменения upstream.
Стоимость разных способов производства не складывается как один общий маршрут.
Однозначные промежуточные рецепты разворачиваются, неоднозначные перечисляются
как требующие выбора. API `/catalog/calculate` принимает `recipe_choices` по api_id;
Desktop пока показывает неоднозначности, без редактора выбора цепочки.
API поддерживает `batch` с `recipe_key` для обычного рецепта; Discord-корзина
предлагает штуки/ящики. MPF считает очереди общим движком с округлением.

Обновление каталога выполняется по TTL, общая PostgreSQL advisory lock защищает
от одновременной синхронизации старым ботом и backend. На сервере Desktop не
скачивает игровые данные самостоятельно.

## Склад и производственные задачи

Миграция `014` добавляет `warehouses`, `stock_balances`, `stock_reservations` и
`production_tasks`. Предметы склада ссылаются на существующий кэш каталога;
игровые стоимости и определения не копируются в отдельную базу.

На странице **Склад** создайте склад, добавьте предмет через общий поиск и
выберите единицу учёта. Новая строка имеет нулевой остаток. Кнопка
«Указать фактический остаток» сохраняет результат инвентаризации с причиной.
Штуки и ящики учитываются отдельно: автоматической конвертации нет.

**Зарезервировать** связывает количество с выбранным открытым заказом. Показаны
фактическое, зарезервированное и доступное количества. На вкладке «Резервы»:

- «Освободить» возвращает количество в доступное, не меняя фактическое.
- «Списать» уменьшает фактическое количество и закрывает резерв.

Списание всего резерва выполняется явно после фактической выдачи. Для частичных
выдач создавайте отдельные резервы. Резервы могут покрывать как готовые предметы,
так и материалы для производства заказа. Нельзя уменьшить остаток ниже резерва,
зарезервировать сверх доступного или повторно списать закрытый резерв. Изменения
защищены блокировками PostgreSQL и версиями; повтор создания с тем же ключом
не создаёт дубль. История операций записывается в существующий AuditLog.

На странице **Производство** создайте задачу для заказа: название этапа, план и
единица (штуки, ящики, партии). Например, «Falchion», «AM4», «Upgrade Spatha».
«Принять» атомарно назначает сотрудника, «Указать готовность» задаёт количество
готового, а не добавляет его повторно. При достижении плана задача завершена.
Готовность не уменьшается; ошибочный этап можно отменить и создать исправленный.
Задачи не списывают склад и не меняют статус заказа автоматически.

Создавать склады могут ADMIN/MANAGER; остатки и резервы меняют также LOGISTICIAN.
DELIVERY может списывать и освобождать резервы. Производством управляют
ADMIN/MANAGER/PRODUCTION/LOGISTICIAN; чужую задачу меняет только руководитель.
Все сотрудники CRM могут читать данные; игроки и BOT без делегирования не имеют
доступа к складу/производству. Обычный логист ограничен свободными и своими заказами.

Перед завершением, отменой или отклонением заказа нужно закрыть его активные
резервы и завершить/отменить задачи, включая административный переход.
Это предотвращает потерю резервов при закрытии. Desktop получает события
`inventory.*` и `production.*` через существующий WebSocket. Фильтры по ID заказа
используют внутренний ID, показанный в заголовке карточки заказа; при создании
задач и резервов заказ выбирается по публичному номеру и заказчику.

## События, ошибки и проверка

Состояние заказа, история, outbox и задания Discord записываются одной транзакцией.
PostgreSQL LISTEN/NOTIFY будит WebSocket; курсор позволяет повторить пропущенные
события. Heartbeat 20 секунд перепроверяет авторизацию и восстанавливает чтение;
нет опроса БД каждую секунду. WS-токен передаётся первым сообщением, не в URL.

Discord worker арендует одно задание на guild на 5 минут; ошибки повторяются
с задержкой, после пяти попыток доступны администратору. Уведомление сохраняет
статус события даже при последующих изменениях заказа. Отправка в Discord имеет
семантику at-least-once: сохранённые ID и поиск маркера среди последних 100 сообщений
сокращают повторы, но Discord и PostgreSQL не имеют общей транзакции, поэтому
абсолютная гарантия отсутствия дублей после сбоя между отправкой и записью невозможна.

Тесты запускать только на отдельной расходной БД: они создают записи и не очищают
все тестовые guild. Подготовьте её миграциями, затем:

```powershell
.venv/Scripts/python.exe -m pip install -r requirements-test.txt -r requirements-desktop.txt
$env:CRM_TEST_DATABASE_URL='postgresql+asyncpg://USER:PASSWORD@127.0.0.1:5432/hector_test'
.venv/Scripts/python.exe -m pytest -q
```

Без CRM_TEST_DATABASE_URL интеграционные PostgreSQL-тесты пропускаются; без
PySide6 пропускаются Qt-тесты. Проверяются concurrency, версии, права, изоляция guild,
идемпотентность, снимки, WebSocket replay, аренда заданий, persistent views,
корзина, API-вызовы Kanban и запуск всех страниц. Реальный Discord gateway и
контейнерная сборка требуют отдельного серверного smoke test после настройки.


## HTTPS для Desktop и Android

Рабочий адрес Hector: `https://103.56.84.85:8443`. В приложении нужен персональный
ключ сотрудника. SSH-туннель на компьютере для этого адреса не требуется.
Порт 443 остаётся за Xray/VPN; backend по-прежнему привязан к 127.0.0.1:8000.

HTTPS запускается дополнительным Compose-файлом:

```bash
cd /opt/AFC-ticket-bot
docker compose -f docker-compose.yml -f docker-compose.https.yml up -d --no-deps https
```

Сертификат Let's Encrypt для IP хранится только на сервере в
`/etc/hector/letsencrypt`; в Git его нет. Срок сертификата — шесть дней.
`deploy/hector-cert-renew.service` и `.timer` установлены в `/etc/systemd/system/`.
Таймер проверяет продление дважды в сутки, после успешной проверки перезагружает
nginx. Для ACME-проверки Certbot временно занимает свободный порт 80. Не занимайте
этот порт другим сервисом без перенастройки способа продления.

```bash
systemctl status hector-cert-renew.timer
journalctl -u hector-cert-renew.service -n 20 --no-pager
```

При первоначальной установке сертификата на этот сервер:

```bash
install -d -m 700 /etc/hector/letsencrypt
docker run --rm -p 80:80 -v /etc/hector/letsencrypt:/etc/letsencrypt certbot/certbot:v5.4.0 certonly --standalone --non-interactive --agree-tos --register-unsafely-without-email --preferred-profile shortlived --ip-address 103.56.84.85
ufw allow 8443/tcp
install -m 644 deploy/hector-cert-renew.service deploy/hector-cert-renew.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now hector-cert-renew.timer
```


## Android

Первая мобильная версия Hector рассчитана на Android 8.0 и новее. APK:
`dist/Hector-Android.apk`. Скопируйте файл на телефон, откройте его и разрешите
установку для приложения, которым открыли APK. Войдите с персональным ключом
сотрудника; HTTPS-адрес уже заполнен. На этом ПК выданный ключ находится в
`C:\Users\myhun\.ssh\afc-desktop-token.txt`. Не передавайте его другим сотрудникам:
для них выдаются отдельные ключи с нужными ролями.

Мобильный клиент поддерживает просмотр и принятие заказов, смену статуса, заметки
и историю, фактические остатки, создание складов/позиций из каталога, резервирование
и списание, производственные задачи и расчёт ресурсов. Есть поиск и постраничная
загрузка. Обновления приходят через WSS, соединение восстанавливается после
возврата в приложение. Фоновые push-уведомления в эту версию не входят.
Настройка Discord, пользователей, ролей и редактирование рецептов доступны в Desktop.

Ключ на Android зашифрован ключом устройства из Android Keystore; резервное
копирование приложения отключено. Выход удаляет сохранённый ключ. Бот-токен,
ключи подписи и приватные данные не включены в APK. HTTP и перенаправления запрещены.

Исходники находятся в `android/`: Kotlin/Compose, существующие REST/WSS API.
Схема БД и серверная бизнес-логика для мобильного клиента не меняются.
Для сборки нужны JDK 17, Android SDK 35 / build-tools 35.0.0, Gradle 8.11.1
(есть Wrapper). `android/build-apk.ps1` собирает release, запускает unit-тесты
и lint, затем подписывает и проверяет APK. В этой рабочей копии инструменты
установлены отдельно в игнорируемый каталог `.tools/android-toolchain`.

Для выпуска обновлений сохраните оба приватных файла из `C:\Users\myhun\.ssh`:
`hector-android-release.jks` и `hector-android-signing-password.txt`. Не добавляйте
их в Git и не публикуйте. Обновления должны подписываться тем же ключом; для
нового выпуска увеличивайте `versionCode` в `android/app/build.gradle.kts`.
